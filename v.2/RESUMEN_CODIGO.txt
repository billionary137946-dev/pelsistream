PELI STREAMS v2 — RESUMEN DEL PROYECTO (qué hace cada archivo)
================================================================
Sistema de apuestas ("palenques"/rifas de color rojo-verde y quinielas) hecho
con Google Apps Script + HTML, sobre Google Sheets como base de datos. Hay 3
roles: admin, operador y cliente, más una página pública de registro.

Este resumen está verificado función por función contra el código actual
(1,442 líneas en codigo.gs). Incluye las optimizaciones de rendimiento, las
protecciones contra conexión mala y las correcciones de bugs ya aplicadas.

------------------------------------------------------------
1) codigo.gs — Backend (Google Apps Script) — 1,442 líneas
------------------------------------------------------------
Es el servidor. Todo lo demás (los .html) solo pide datos a estas funciones
vía google.script.run. Se conecta a UNA hoja de cálculo (SS_ID) con 4 pestañas:

  - LOGIN: una fila por usuario (admin/operador/cliente) → celular, password,
    rol, alias, saldo, limite_credito, negocio_id, estatus, fecha_registro.
  - NEGOCIOS: una fila por casa de apuestas → nombre, activo, max_operadores,
    corretaje_pct (% que se queda la casa), fecha, creado_por.
  - JUGADAS: una fila por apuesta → tipo, evento, cliente, color, monto,
    corretaje, resultado, neto, operador, fecha.
  - MOVIMIENTOS: histórico de saldo de cada cliente (depósitos, apuestas,
    ganancias, ajustes) → cliente, tipo, palenque, monto, saldo antes/después,
    fecha, operador.

Bloques principales del archivo:

  • Definición de columnas de las 4 hojas (objetos LOGIN/NEGOCIOS/JUGADAS/
    MOVIMIENTOS) — mapa entre nombre de campo y encabezado real de la hoja.

  • Helpers de hoja:
    - ss()/hoja(): abre el spreadsheet y devuelve una pestaña (o error claro
      si no existe).
    - L(v): limpia valores vacíos/"nan"/"undefined" que llegan de la hoja.
    - _headerRow(): detecta en qué fila están los encabezados (por si hay
      filas vacías antes).
    - leerHoja(): lee una pestaña completa y la convierte en array de objetos
      {columna: valor}; nunca lanza error, si falla regresa [] y loggea.

  • Caché de LOGIN por ejecución (_loginIndex/_invalidarLoginCache):
    LOGIN se consultaba decenas o miles de veces por request — funciones
    como getEventosAbiertos, getNumerosUsados, getHistorialJugadas y
    declararGanadorEvento llaman _negocioDeCliente (que depende de LOGIN)
    UNA VEZ POR CADA FILA de JUGADAS. Ahora _loginIndex() lee LOGIN una sola
    vez por ejecución y la indexa por celular; _buscarUsuarioPorCelular()
    consulta ese índice en vez de releer la hoja. Las 7 funciones que
    escriben en LOGIN (crearOperador/crearCliente, editarOperador/
    editarCliente, registrarCliente, completarYActivarCliente,
    registrarApuesta, declararGanadorEvento, editarApuestaPendiente) llaman
    _invalidarLoginCache() justo después de escribir, para que ninguna
    lectura posterior dentro de la misma ejecución sirva un saldo/estatus
    viejo.

  • Caché de JUGADAS por ejecución, solo lectura (_jugadasRaw):
    getResumenInicio pide tanto el resumen (_jugadasEnRango) como la serie de
    la gráfica (_serieParaFiltro/_corretajePorMes) en una sola llamada — antes
    esto leía la hoja JUGADAS completa DOS veces por cada carga del
    dashboard. Ahora las tres comparten una sola lectura cruda de la hoja.
    Ninguna de las tres escribe en JUGADAS, así que no necesita invalidación.

  • Dedupe de intentos por conexión mala (_resultadoDeIntento/
    _recordarIntento): usa CacheService (persiste 5 min entre ejecuciones,
    a diferencia de una variable normal) para recordar el resultado de un
    "intento_id" que manda el cliente. Si la respuesta de registrarApuesta
    o cerrarQuiniela se pierde por una conexión mala y el navegador reintenta
    con el MISMO intento_id, el backend regresa el resultado ya calculado sin
    repetir el cobro/pago. declararGanadorEvento no lo necesita: ya es
    idempotente por diseño (reintentar un evento ya cerrado simplemente no
    encuentra apuestas pendientes).

  • Autenticación y sesión:
    - _buscarUsuarioPorCelular(): busca un usuario por celular en LOGIN
      (vía el caché de arriba).
    - validarLogin(celular, password): valida credenciales, revisa estatus
      (inactivo/pendiente) y rol; si todo bien regresa datos de sesión + la
      URL de la app.
    - validarSesion(celular, rolEsperado): revalida que el usuario siga
      existiendo, activo y con el rol correcto ANTES de servir un panel —
      evita que alguien entre a /admin cambiando la URL o que una cuenta
      desactivada siga operando.

  • Router (doGet): decide qué página HTML servir según el parámetro "vista"
    (login/registro/admin/operador/cliente), revalidando sesión en las vistas
    protegidas. Soporta el modo "embed=netlify" para cuando la app corre
    dentro de un iframe (navega por postMessage en vez de mover la URL de
    arriba). Si algo truena, muestra una pantalla de error amigable en vez
    del error genérico de Google.
    - _servir(): carga la plantilla HTML y le inyecta variables (celular,
      alias, negocio_id, embed, url).
    - getAppUrl(): URL pública del Web App.

  • Dashboard del Admin ("Inicio"):
    - _contarClientesEnDeuda(): cuenta clientes con saldo negativo (usa el
      caché de LOGIN).
    - _corretajePorMes()/_lunesDe()/_serieParaFiltro(): construyen la serie
      de datos para la gráfica de corretaje, con distinta granularidad según
      el filtro (día en "semana", semana lunes-a-lunes en "mensual", mes en
      "anual"). Usan el caché de JUGADAS crudo.
    - _jugadasEnRango(): recorre JUGADAS una vez y devuelve totales
      (jugadas/volumen/corretaje) + detalle, dentro de un rango de fechas.
    - getResumenInicio(): resumen completo para las tarjetas + gráfica de
      Inicio, según el filtro Hoy/Semana/Mes/Todo.
    - getDetalleCorte(): detalle de una barra específica de la gráfica (al
      hacer clic).
    - getHistorialOperador(): historial completo de jugadas de un operador
      (para que el admin lo revise).

  • Negocios (sub-tab "Mi Negocio"):
    - getNegocios(): lista todos los negocios.
    - crearNegocio(): crea un negocio nuevo (máx. 5 activos, nombre único).
    - editarNegocio(): edita corretaje/máx. operadores/activo (el nombre no
      se puede cambiar porque es la clave que relaciona usuarios).

  • Operadores y clientes (ambos viven en LOGIN, solo cambia el "rol"):
    - getOperadores()/getClientes(): listan usuarios por rol (usan el caché
      de LOGIN).
    - _crearUsuarioLogin()/crearOperador()/crearCliente(): dan de alta un
      usuario nuevo.
    - _editarUsuarioLogin()/editarOperador()/editarCliente(): editan alias,
      negocio, estatus, password (opcional) y, si es cliente, saldo/límite.

  • Auto-registro público (registro.html, sin sesión):
    - registrarCliente(): crea la cuenta en estatus "pendiente" (no puede
      entrar hasta que el admin la active) — evita altas no autorizadas.
    - getNegocioPublico(): devuelve el nombre del negocio si existe/está
      activo, para mostrarlo en el formulario público.
    - completarYActivarCliente(): para clientes auto-registrados, el admin
      completa saldo/límite de crédito y activa en un solo paso.

  • Panel Operador — Jugadas (apuestas rojo/verde):
    - _negocioDeCliente()/_corretajePctDe(): resuelven el negocio de un
      usuario y el % de corretaje de ese negocio.
    - getClientesPorNegocio(): clientes activos del negocio del operador (el
      negocio se calcula desde el celular del operador, nunca desde el
      navegador, para que no pueda ver clientes de otro negocio).
    - registrarApuesta(): revisa primero si "intento_id" ya se procesó
      (dedupe); valida que el cliente exista (mensaje correcto "Cliente no
      encontrado" antes de comparar negocio — corregido), que sea del mismo
      negocio, color/monto/saldo-crédito; descuenta el saldo de inmediato, y
      guarda la apuesta en JUGADAS como pendiente (Resultado vacío) + el
      movimiento en MOVIMIENTOS.
    - getNumerosUsados(): números de "palenque #N" ya usados para evitar
      duplicados entre operadores/sesiones.
    - getEventosAbiertos(): eventos con apuestas pendientes del negocio, con
      volumen por color, para elegir cuál cerrar.
    - declararGanadorEvento(): cierra un evento — calcula corretaje/neto de
      cada apuesta pendiente y acredita a los que acertaron. Soporta
      resultado rojo/verde (paga al que acertó), empate/cancelada (regresa el
      monto íntegro a todos, sin corretaje, y guarda Neto=0 — corregido: antes
      guardaba el monto original como si fuera ganancia).

  • Quinielas (Ventaja / Quiniela / Mano a mano / Pares y nones):
    - cerrarQuiniela(): revisa "intento_id" (dedupe) igual que registrarApuesta;
      a diferencia de las apuestas normales, la quiniela se registra completa
      de un solo golpe en JUGADAS al cerrarla (los apostadores normalmente no
      tienen cuenta, pagan en efectivo).

  • Panel Cliente:
    - getSaldoCliente(): saldo actual (para refrescarlo sin recargar todo).
    - getHistorialCliente(): historial de jugadas propias del cliente.

  • Historial y edición:
    - getHistorialJugadas(): historial de jugadas de todo el negocio del
      operador.
    - editarApuestaPendiente(): permite corregir monto/color de una apuesta
      MIENTRAS siga pendiente (Resultado vacío); ajusta el saldo del cliente
      por la diferencia y deja el ajuste en MOVIMIENTOS. Si el cliente de esa
      apuesta ya no existe en LOGIN, ahora regresa error en vez de actualizar
      el monto/color sin ajustar el saldo (corregido). Una vez cerrada la
      apuesta ya no se puede editar (descuadraría lo ya pagado/cobrado).

------------------------------------------------------------
  • Formulario de celular + contraseña (con botón para mostrar/ocultar

    animaciones de fondo (orbes flotantes).

4) admin.html — Panel del administrador — 1,744 líneas
------------------------------------------------------------
Panel con navegación por tabs (goTab). Secciones principales:

  • Inicio (dashboard):
    - Filtro de corte Hoy/Semana/Mes/Todo (setFiltroInicio) que recalcula
      tarjetas (jugadas, volumen, corretaje, clientes en deuda) y la gráfica
      de barras de corretaje (renderGrafica), pidiendo datos a
      getResumenInicio().
    - Al hacer clic en una barra de la gráfica se abre un modal con el
      detalle de ese corte (abrirModalDetalleCorte → getDetalleCorte), con
      opción de exportar ese detalle a CSV (btnExportarCorte).
    - Modal de historial de un cliente (abrirModalHistCliente →
      getHistorialCliente) y de un operador (abrirModalHistOperador →
      getHistorialOperador), accesibles desde las tarjetas de jugadas.

  • Mi Negocio (con sub-tabs: Negocios / Operadores / Clientes):
    - Negocios: lista, alta (crearNegocio) y edición (editarNegocio) de
      negocios; botón para copiar el link público de registro de cada
      negocio (_copiarLinkRegistro).
    - Operadores: lista, alta (crearOperador) y edición (editarOperador),
      con buscador y activar/desactivar.
    - Clientes: lista, alta (crearCliente), edición (editarCliente),
      buscador, y flujo especial para clientes auto-registrados en
      "pendiente" (abrirModalActivar → completarYActivarCliente), donde el
      admin completa saldo/límite y los activa.

  • Resiliencia ante conexión mala: los 4 formularios de escritura (Negocio,
    Operador, Cliente, Activar cliente) usan _avisarSiTarda() — si el
    servidor no responde en 9s, muestra "Tu conexión está lenta, espera un
    momento…" sin cancelar la petición, en vez de dejar el botón "Guardando…"
    congelado sin explicación.

  • Helpers de UI compartidos: formateo de dinero, tarjetas de jugada
    reutilizadas en los 3 modales, armado del <select> de negocios, exportar
    a CSV, etc.

5) operador.html — Panel del operador — 1,711 líneas
------------------------------------------------------------
Es donde se registran las apuestas y se cierran los eventos. Tiene 3
áreas principales (por tabs):

  • Registrar apuesta:
    - Sistema de "5 slots" en paralelo: el operador puede tener hasta 5
      jugadas/eventos abiertos a la vez (uno por slot) y cambiar entre ellos
      (_cargarSlot, _guardarSlotActual, _actualizarDisponibilidadSlots).
    - Elige tipo de jugada (Apuesta rojo/verde vs. Quiniela) con tipo-btn.
    - Autocompletado de cliente por alias/celular: un <input> de texto (NO un
      <select>) que filtra en vivo contra _cacheClientesNegocio (cargado con
      getClientesPorNegocio); el botón de color no se habilita si no se
      eligió un cliente real de la lista de sugerencias — nunca texto libre.
    - Botones de color rojo/verde que registran la apuesta al tocarlos
      (_intentarRegistrarApuesta → registrarApuesta), mandando un
      "intento_id" estable mientras se reintente la MISMA apuesta (mismo
      evento+cliente+color+monto) — protege contra duplicar el cobro si la
      respuesta se pierde por conexión mala. Se libera (id nuevo) en cuanto
      la apuesta tiene éxito. Aviso de "conexión lenta" a los 9s.
    - Valida contra getNumerosUsados() que el número de palenque no esté
      repetido.
    - Quinielas: subtipos Ventaja/Quiniela/Mano a mano/Pares y nones,
      permite agregar varios apostadores (_renderApostadores) y cerrar todo
      de una vez (btnCerrarQuiniela → cerrarQuiniela), con el mismo patrón de
      "intento_id" estable por slot (s._intentoCierreId) + aviso de conexión
      lenta.
    - Tiene un "modo prueba": si no existe google.script.run (probando el
      HTML fuera de Apps Script), simula respuestas con datos mock en vez de
      llamar al backend.

  • Eventos abiertos / Cerrar apuesta:
    - Lista eventos pendientes del negocio (cargarEventosAbiertos →
      getEventosAbiertos) con su volumen por color.
    - Modal "¿Quién ganó?" (abrirModalResultado) para declarar
      rojo/verde/empate/cancelada, que llama a declararGanadorEvento (con
      aviso de conexión lenta; no necesita intento_id porque ya es
      idempotente del lado del backend).

  • Historial:
    - Lista de jugadas del negocio (cargarHistorial → getHistorialJugadas),
      con filtro y tarjetas.
    - Permite editar una apuesta aún pendiente (modal "editar apuesta" →
      editarApuestaPendiente, con aviso de conexión lenta): solo monto y
      color, con límites $500–$1,000,000.

  • Común: sesión (quién soy, negocio), navegación por tabs, atajos de
    teclado, cerrar sesión, helper _avisarSiTarda() compartido por las 4
    acciones de escritura de este panel.

6) cliente.html — Panel del cliente — 329 líneas (el más simple)
------------------------------------------------------------
  • Al entrar, valida sesión y pinta el saldo actual (_pintarSaldo), con
    polling automático cada 5s (_iniciarPollingSaldo → getSaldoCliente) para
    que el saldo se actualice solo mientras el cliente tiene la página
    abierta (por si un operador le liquida una apuesta). El polling tiene
    una bandera de "ya hay una petición en curso" (_pollEnCurso): si una
    respuesta tarda más de 5s por conexión mala, el siguiente tick se salta
    en vez de encimar peticiones.
  • Historial propio: lista de sus jugadas (cargarHistorialCliente →
    getHistorialCliente), con tarjetas por jugada y filtro.
  • Botón de cerrar sesión / volver al login, mismo esquema visual dorado/
    marino que el resto del sistema.
  • Es de solo lectura: no tiene ninguna llamada de escritura (crear/editar/
    registrar) — verificado, ninguna función del cliente modifica datos.

FLUJO GENERAL
------------------------------------------------------------
1. Cliente nuevo entra por un link de registro.html → queda "pendiente".
2. Admin lo activa (o lo completa+activa si faltan saldo/límite) desde
   admin.html.
3. Cliente y operador entran por login.html; el rol decide qué panel se
   sirve (doGet valida sesión en cada carga).
4. Operador registra apuestas de sus clientes desde operador.html (se
   descuenta saldo al instante, con protección anti-duplicado por
   intento_id).
5. Operador cierra el evento declarando el color ganador (o empate/
   cancelada); a los que acertaron se les acredita el neto y se calcula el
   corretaje para la casa.
6. Admin ve todo el negocio consolidado (jugadas, volumen, corretaje,
   clientes en deuda) desde el dashboard de admin.html.

ESTADO DE LA REVISIÓN (última pasada quirúrgica, función por función)
------------------------------------------------------------
  ✔ Las 41 funciones de codigo.gs revisadas una por una.
  ✔ Los 26 puntos de llamada google.script.run en los 5 HTML cruzados contra
    las firmas reales del backend — todos coinciden.
  ✔ Sintaxis válida en los 6 archivos (verificado con parser de Node).
  ✔ 3 bugs preexistentes encontrados y corregidos:
    1. registrarApuesta: mensaje "Cliente no encontrado" ahora sale antes
       que "no pertenece a tu negocio" cuando el celular no existe.
    2. declararGanadorEvento: Neto ya no guarda el monto original en
       empate/cancelada (ahora guarda 0, que es el neto real).
    3. editarApuestaPendiente: si el cliente ya no existe en LOGIN, regresa
       error en vez de actualizar monto/color sin ajustar el saldo.
  ⚠ Limitación conocida (no es un bug, es un límite de diseño): el dedupe
    por intento_id solo protege reintentos mientras la página sigue abierta;
    una recarga completa después de un timeout pierde esa protección.
  ✔ 5 bugs adicionales encontrados en una segunda pasada y ya corregidos en
    codigo.gs (sintaxis reverificada con parser de Node tras los cambios):
    4. crearNegocio: no validaba que corretaje_pct estuviera entre 0 y 100
       (editarNegocio sí lo validaba) — ahora usa la misma validación.
    5. editarNegocio: reactivar un negocio (activo:false → true) no
       respetaba el límite de 5 negocios activos que sí aplica crearNegocio
       — ahora cuenta los negocios activos restantes antes de reactivar.
    6. registrarApuesta: no revalidaba que el cliente siguiera con estatus
       'activo' del lado del servidor antes de cobrarle — solo se filtraba
       en el buscador del operador (getClientesPorNegocio). Ahora regresa
       error si el cliente no está activo.
    7. editarApuestaPendiente: mismo caso que el punto 6 — ahora también
       exige que el cliente esté activo antes de ajustar su saldo.
    8. _crearUsuarioLogin (crearOperador): el campo max_operadores de
       NEGOCIOS se guardaba y editaba desde admin.html pero nunca se
       comparaba contra el número real de operadores activos del negocio —
       el límite existía solo como dato, no como regla aplicada. Ahora
       crearOperador lo valida antes de dar de alta.

SECUENCIA DE PASOS DEL SISTEMA (para reconstruir en React — sin Apps Script)
------------------------------------------------------------
Esto describe el comportamiento en términos genéricos (pantallas, acciones de
usuario, llamadas a un backend/API, estado en una base de datos), sin nombrar
conceptos propios de la plataforma actual — para usarse como guía de flujo al
construir la versión en React sin arrastrar vocabulario de la implementación
vieja.

1. REGISTRO PÚBLICO
   1.1 Un visitante abre un link con un identificador de negocio en la URL.
   1.2 La app pide al backend el nombre de ese negocio; si no existe o está
       inactivo, muestra "link inválido" y oculta el formulario.
   1.3 El visitante llena alias, celular y contraseña, y envía.
   1.4 El backend crea la cuenta con estado "pendiente" y responde éxito.
   1.5 La app muestra un mensaje: la cuenta debe ser activada por un
       administrador antes de poder entrar.

2. INICIO DE SESIÓN
   2.1 El usuario ingresa celular + contraseña.
   2.2 El backend valida credenciales, estado de la cuenta (activo/inactivo/
       pendiente) y rol.
   2.3 Si es válido, la app guarda la sesión (token) y redirige a la pantalla
       que corresponde al rol: administrador, operador o cliente.
   2.4 En cada carga posterior de una pantalla protegida, la app revalida la
       sesión contra el backend (rol y estado siguen siendo válidos) antes de
       mostrar datos — nunca confía solo en lo que quedó guardado localmente.

3. ADMINISTRADOR — configuración
   3.1 Crea o edita negocios (nombre único, máximo 5 negocios activos al
       mismo tiempo, cada uno con su propio porcentaje de comisión y límite
       de operadores).
   3.2 Da de alta o edita operadores y clientes, asignándolos a un negocio.
   3.3 Revisa la lista de clientes en estado "pendiente" (llegados por
       registro público) y los activa completando su saldo inicial y límite
       de crédito.
   3.4 Comparte el link de registro público de cada negocio.

4. ADMINISTRADOR — panel de control
   4.1 Elige un rango de tiempo (hoy / semana / mes / todo).
   4.2 La app pide al backend el resumen de ese rango: número de apuestas,
       volumen apostado, comisión generada, número de clientes con saldo
       negativo, y una serie de datos para graficar (agrupada por día,
       semana o mes según el rango elegido).
   4.3 Al seleccionar un punto de la gráfica, pide el detalle de ese corte
       específico (lista de apuestas que lo componen) y permite exportarlo.
   4.4 Puede abrir el historial completo de cualquier cliente u operador.

5. OPERADOR — capturar una apuesta
   5.1 El operador elige el tipo de juego (apuesta de dos colores, o
       quiniela) dentro de uno de sus varios espacios de trabajo en paralelo
       (para llevar varios eventos abiertos a la vez).
   5.2 Busca al cliente por alias o celular entre los clientes activos de su
       propio negocio (nunca puede ver ni elegir clientes de otro negocio, y
       nunca puede escribir un nombre que no exista en la lista).
   5.3 Ingresa el monto y confirma el color elegido.
   5.4 La app manda la apuesta al backend con un identificador de intento
       fijo para esa apuesta concreta: si la respuesta no llega (mala señal)
       y la app reintenta el mismo envío, el backend reconoce que ya se
       procesó y no vuelve a cobrar.
   5.5 El backend valida: cliente existe, está activo, pertenece al mismo
       negocio del operador, el monto no deja al cliente por debajo de su
       límite de crédito. Si todo pasa, descuenta el saldo del cliente DE
       INMEDIATO y guarda la apuesta como pendiente (sin resultado todavía).
   5.6 La app confirma visualmente que la apuesta quedó registrada.

6. OPERADOR — cerrar un evento
   6.1 El operador ve la lista de eventos con apuestas todavía pendientes de
       su negocio, con el total apostado por cada color.
   6.2 Elige un evento y declara el resultado: color ganador, empate, o
       cancelado.
   6.3 El backend recorre todas las apuestas pendientes de ese evento (de su
       negocio): si el resultado es un color, paga a quienes acertaron
       (monto menos comisión) y no le regresa nada a quienes perdieron (ya
       se les había cobrado al apostar); si es empate o cancelado, regresa
       el monto completo a todos, sin cobrar comisión a nadie.
   6.4 Cada apuesta pagada/devuelta actualiza el saldo del cliente
       correspondiente y queda un registro del movimiento.
   6.5 Cerrar el mismo evento dos veces no causa doble pago: la segunda vez
       simplemente no encuentra apuestas pendientes que tocar.

7. OPERADOR — quiniela (varios apostadores de una vez)
   7.1 El operador agrega varios apostadores a una misma quiniela (nombre,
       lugar elegido, y quién ganó).
   7.2 Al cerrar, la app manda todos los apostadores juntos en un solo envío
       (con su propio identificador de intento para evitar duplicados).
   7.3 El backend calcula comisión/ganancia de cada apostador y guarda todo
       ya resuelto de una vez — a diferencia de una apuesta normal, aquí no
       queda "pendiente": se registra ganada o perdida en el mismo paso.

8. OPERADOR — editar una apuesta pendiente
   8.1 Desde el historial, el operador puede corregir monto o color de una
       apuesta que SIGUE pendiente (dentro de límites de monto permitidos).
   8.2 El backend ajusta el saldo del cliente por la diferencia entre el
       monto viejo y el nuevo, valida que el cliente siga activo y con
       crédito suficiente, y deja registrado el ajuste.
   8.3 Una apuesta ya cerrada no se puede editar.

9. CLIENTE — panel de solo lectura
   9.1 Al entrar, ve su saldo actual.
   9.2 La app vuelve a pedir el saldo automáticamente cada pocos segundos
       mientras la pantalla sigue abierta, para reflejar sin recargar si un
       operador le acaba de pagar una apuesta.
   9.3 Puede ver su propio historial de apuestas (pendientes y resueltas).
   9.4 No existe ninguna acción de escritura en este rol: todo lo que ve es
       resultado de lo que hicieron el operador o el administrador.

Esta secuencia (1 a 9) es la que debe reproducir la app de React consumiendo
un backend en Python vía API — el "cómo" cambia de tecnología, pero el orden
de los pasos y las reglas de validación en cada uno deben mantenerse igual.
